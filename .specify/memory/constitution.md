# Divisor de Cuenta Constitution

## Core Principles

### I. SOLID Code Quality

The code MUST respect SOLID in a way that can be checked in review:

- SRP: each class has one reason to change. Calculation logic MUST NOT validate
  user input or format display strings.
- OCP: adding a new rounding rule MUST be possible by adding a new implementation
  of a domain abstraction, without editing existing calculation classes.
- LSP: any implementation of a domain interface MUST be replaceable by another
  implementation without type checks by the caller.
- ISP: interfaces MUST stay small. A class MUST NOT depend on methods it does not
  use.
- DIP: `presentation` MUST depend on abstractions from `domain`, never on concrete
  classes from `data`.

Rationale: the comparison requires maintainable code whose design decisions are
visible and testable, not only working UI code.

### II. Layered Architecture

Application code MUST be organized in these layers:

- `lib/presentation`
- `lib/domain`
- `lib/data`

The dependency rule is:

```text
presentation -> domain <- data
```

`lib/domain/` MUST NOT import `package:flutter`. The domain layer MUST be pure
Dart. `main.dart` MUST be the only place where concrete implementations are
instantiated and wired together.

Rationale: the domain calculation must remain independent from Flutter and easy
to test without UI dependencies.

### III. Repository Security

Secrets, API keys, credentials, personal tokens, and generated private agent
state MUST NOT be committed to the repository. Any required secret MUST be kept
outside version control and documented by name only.

Rationale: this project is stored in Git and may be pushed to GitHub.

### IV. Critical Tests

Every critical behavior MUST have executable tests. For each feature spec, every
acceptance criterion MUST become at least one automated test or be explicitly
marked as manually verified with the reason automation was not possible.

Rationale: the practice compares approaches using evidence, so acceptance must
be verifiable by commands or documented manual checks.

### V. Student Explainability

Every function generated by the agent MUST be explainable by the student. For
each function, the student must be able to state what it does, why it exists,
what it receives, what it returns, and what errors or invalid states it handles.

Rationale: generated code is acceptable only when the student can defend and
maintain it.

## Architecture Rules

The MVP scope is a one-screen Flutter bill splitter. It accepts total amount,
number of people, and tip percentage, then displays how much each person pays.
New behavior MUST stay inside that product scope unless a later specification
explicitly expands it.

Domain objects and services MUST use Spanish names when they represent product
concepts. UI text MUST be understandable for Spanish-speaking users. No external
Flutter or Dart packages may be added unless the need is documented before the
dependency is introduced.

## Quality Gates

Before a feature is considered complete, the following checks MUST be attempted:

- `flutter analyze`
- `flutter test`

If a command cannot run because of environment problems, the failure mode MUST be
recorded in `bitacora.md` or the feature artifacts. Any manual verification used
instead MUST include the scenario, inputs, expected result, and observed result.

Code review MUST check that `domain` has no Flutter imports, that concrete
implementations are only wired in `main.dart`, and that adding a new rounding
rule does not require modifying existing calculation classes.

## Governance

This constitution supersedes informal preferences for this project. Feature
specifications, plans, tasks, implementation, and reviews MUST comply with these
rules.

Amendments require a direct change to `.specify/memory/constitution.md` with a
clear reason. Version changes follow semantic versioning:

- MAJOR: removes or redefines a core principle.
- MINOR: adds a new principle or expands governance materially.
- PATCH: clarifies wording without changing obligations.

Compliance MUST be reviewed during SDD planning and after implementation. Any
known violation MUST either be fixed before completion or documented as a
deferred risk with a concrete follow-up task.
